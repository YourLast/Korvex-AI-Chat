# Deploying

Korvex AI Chat is one container with a persistent disk: the SQLite database, uploaded files and the encryption key live in `/data`.
Any host that runs a Docker image with a disk works.

## Your own server

```bash
docker compose up -d
```

`compose.yaml` starts four containers:

- **app** — the chat itself;
- **ollama** — the built-in local model (IBM Granite 4 Micro, Apache 2.0). It downloads on the first start (2.1 GB) and appears in
  **Admin → Models** by itself; titles of chats and user memory use it too;
- **search** — SearXNG for the web search tool;
- **stt** — speaches (faster-whisper) for voice input.

Put the app behind HTTPS (Caddy, nginx, Traefik) and set `COOKIE_SECURE=1`.

**GPU.** With an NVIDIA GPU and the NVIDIA Container Toolkit the local model runs on the GPU:

```bash
docker compose -f compose.yaml -f compose.gpu.yaml up -d
```

**Tools.** Models with tools on (the local model, OpenAI, Anthropic …) can search the web, remember things about the user
and read other chats. The schemas of the tools add about 1,400 tokens to a request: on a slow CPU the first answer of a chat
starts later (the local model then keeps them in its cache). `KX_AGENT_TOOLS=0` turns tools off.

**Another local model.** Put `KX_LOCAL_MODEL=<name from ollama.com/library>` into `.env` next to `compose.yaml` before the
first start (later: add the model in **Admin → Models** under the Ollama provider). `KX_LOCAL_MODEL=` (empty) — no local
model: add models by API in **Admin → Models** instead.

## Home servers: CasaOS, ZimaOS, Unraid, Coolify

Ready templates are in [deploy/](../deploy/). Each pins the image of this release.

- **CasaOS / ZimaOS:** App Store → **Custom Install** → **Import**, paste
  [deploy/casaos/docker-compose.yml](../deploy/casaos/docker-compose.yml). It is the full stack of `compose.yaml`: the app,
  the local model, web search and voice input. Data lives in `/DATA/AppData/korvex-ai-chat/`.
- **Unraid:** Docker → **Add Container** → **Template repositories**, add
  `https://github.com/YourLast/Korvex-AI-Chat`, then pick **Korvex-AI-Chat**. It is the app alone. For the local model
  set **Ollama URL** to your Ollama container (Community Applications has one). Optional settings point at SearXNG
  (web search; its `settings.yml` needs `json` in `search.formats`) and speaches (voice input).
- **Coolify:** **New Resource** → **Docker Compose Empty**, paste
  [deploy/coolify/korvex-ai-chat.yaml](../deploy/coolify/korvex-ai-chat.yaml). Coolify gives it a domain. Behind HTTPS
  set `COOKIE_SECURE=1`.

With only **Ollama URL** set, chat titles and user memory use the local model too.

## Render

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/YourLast/Korvex-AI-Chat)

The button reads `render.yaml`: one web service from the Dockerfile and a 5 GB disk at `/data`.
A persistent disk needs a paid instance type.

## Railway

1. **New Project → Deploy from GitHub repo**, pick your fork. `railway.json` tells Railway to build the Dockerfile.
2. Add a **Volume** to the service with the mount path `/data` (Railway configures volumes in the dashboard or with
   `railway volume add`, not in the config file).
3. Set `COOKIE_SECURE=1` and redeploy.

Without the volume the database is lost on every deploy.

## Fly.io

```bash
fly launch --copy-config --no-deploy   # change the app name in fly.toml if it is taken
fly volumes create korvex_data --size 5
fly deploy
```

`fly.toml` keeps one machine running: answers are generated in the background, and an auto-stopped machine would cut them.

## Models on cloud hosts

The cloud configs run only the app, without the local model: add a model by API in **Admin → Models**
(OpenAI, Anthropic, OpenRouter, or any OpenAI-compatible server).

## Voice input and web search on cloud hosts

The cloud configs run only the app. For voice input, point `STT_URL` at any server with an OpenAI-compatible
`/v1/audio/transcriptions` (for example, speaches on the same host, or a hosted speech-to-text API) and set `STT_MODEL`.
For web search, choose Brave Search or Tavily with an API key (both have a free tier) in **Admin → Features**.

## Why not Vercel (yet)

Vercel runs serverless functions, and this app is built as a long-running server:

- **Long answers.** A model can think for many minutes. Here the answer is generated by a background job that survives a
  closed tab; a serverless function is cut at its time limit.
- **Background work.** Jobs, scheduled automations, push notifications and the live event stream run inside the server process.
  Serverless functions stop between requests.
- **SQLite on a local disk.** The database is SQLite with synchronous access throughout the code. Serverless functions have no
  persistent disk.

### What a Vercel version needs

1. A database layer that works with Postgres (Neon or Vercel Postgres): move every database call to async and replace
   SQLite-specific SQL (full-text search with FTS5, JSON functions) with Postgres equivalents.
2. Files in object storage (Vercel Blob or S3) instead of `/data`.
3. Answers generated within one request, limited by the function time limit; no background jobs.
4. Automations through Vercel Cron; the live event stream replaced with polling or a hosted pub/sub.

Until then, use any Docker host above.
